Bloom Filters — the cheat sheet

How an app checks “is this username taken?” against a billion names in an instant — using a tiny row of bits instead of the database.

The one idea
A Bloom filter stores a fingerprint of the set, not the items. It answers “definitely not” or “maybe” — never a certain “yes.”
The mental model

You type a username into an app like Instagram. The instant you stop, it says taken or available — checked against a billion names. Keep every taken name's fingerprint in a Bloom filter: if it says “definitely not in the set,” the name is guaranteed free — answer instantly, no database hit. If it says “maybe,” do one real lookup to confirm. Most names people try are free, so the filter handles the common case alone.

The guarantee
False positives: possible. False negatives: impossible. It might send a free name for one extra check — it never calls a taken name free.

Memorize: ~10 bits per item ≈ 1% false positives with k ≈ 7, and ~half the bits end up set. 1 billion usernames at 1% → ~1.2 GB in RAM (vs ~15 GB to store the names). Size depends on n and p only — not on how long each item is.

Where it's used (and the catch)

#1 use — LSM databases (Cassandra, HBase, Bigtable, RocksDB): a Bloom filter per SSTable answers “could this key be in this file?” so reads skip disk files that definitely don't contain the key. Also: CDNs (Akamai skips caching one-hit-wonders), Postgres bloom index, early Chrome Safe Browsing, Medium (don't re-recommend read articles), distributed caches (skip the RPC).

Can't delete (clearing shared bits would create false negatives) → use a counting Bloom filter or a cuckoo filter (which also supports delete + better cache locality). Don't use when you need exact membership, retrieval, or when a false positive is unsafe.

Interview Q&A

Tap a question. From fundamentals to the tricky follow-ups.

Fundamentals
What is a Bloom filter in one sentence?
A space-efficient probabilistic set that tests membership, answering “definitely not in the set” or “possibly in the set” — with possible false positives but no false negatives.
Does it store the actual items?
No — only a bit array. Items are never kept, so you can't list or retrieve them, and the size is independent of item length.
Why no false negatives, but false positives are possible?
Adding an item sets its k bits to 1, and bits only go 0→1 (never back). So a real member's k bits are always 1 → never “definitely not.” A false positive happens when a non-member's k bits were all coincidentally set by other items.
What are the three parameters and how do they relate?
m (bits), n (items), k (hashes). Optimal k = (m/n)·ln2, giving p = 2^(−k) and m = −n·ln p / (ln2)².
Mechanics & math
If I add more hash functions, does accuracy always improve?
No — there's a sweet spot. Too few hashes under-discriminate; too many fill the array with 1s too fast, raising false positives. Optimum k = (m/n)·ln2 sets ~half the bits to 1.
How much memory for 1B items at 1% FP?
~9.6 bits/item → ~1.2 GB, k ≈ 7. Rule of thumb: ~10 bits/item ≈ 1% FP.
My false-positive rate is too high in production — which knobs?
Increase m (more bits) — the primary lever — and re-tune k to (m/n)·ln2. If n grew beyond plan the filter is over-full → rebuild larger or switch to a scalable Bloom filter. You can't lower FP by deleting (you can't delete).
What happens as the filter saturates?
Bits approach all-1s, so almost every query returns “maybe” and the FP rate → ~1. The filter becomes useless — rebuild it larger.
Operations & limits
Why can't a standard Bloom filter delete?
Clearing an item's bits might clear bits shared with other present items, creating false negatives and breaking the core guarantee.
How do you support deletion then?
Counting Bloom filter (per-slot counters: increment on add, decrement on delete; ~4× space, watch overflow) or a cuckoo filter (stores fingerprints, supports delete). Or periodically rebuild.
Can two Bloom filters be merged?
Yes — same m and hash functions → the union is a bitwise OR. Great for combining per-shard filters. (Intersection via AND is not exact.)
Are they concurrency-friendly?
Reads are naturally concurrent. Inserts only flip bits 0→1, so concurrent inserts are safe without locks in most memory models. Counting filters need atomic counter updates.
Variants & alternatives
Bloom filter vs hash set — when each?
Hash set = exact membership + retrieval, but O(item-size) space and must hold the keys. Bloom = probabilistic, no retrieval, a fraction of the space. Use Bloom as a front-line filter before an exact structure.
Bloom vs Cuckoo filter?
Cuckoo supports deletion, has better cache locality, and is often smaller below ~3% FP. Bloom is simpler with no “insertion can fail” case. Cuckoo is the usual “what if you need deletes?” answer.
Bloom filter vs HyperLogLog?
Different jobs. Bloom = membership (“is X in the set?”). HyperLogLog = cardinality (“how many distinct?”). Don't mix them up.
Systems & design
Where does a Bloom filter appear in Cassandra / RocksDB?
Per SSTable: before reading a file from disk for a key, check that SSTable's Bloom filter. “Definitely not” → skip the disk read. Makes point reads for non-existent keys cheap — the classic LSM-tree optimization.
Design: username availability at scale.
In-RAM Bloom filter of all taken names (sized for n, p=1%). Per keystroke, query it: “definitely not” → available instantly, no DB; “maybe” → one indexed DB lookup to confirm (covers the ~1% FPs). Append on new signups; use a counting filter or periodic rebuild if names get freed.
A false positive caused an extra DB read — is that a bug?
No — expected by design. You pick the direction so a false positive is merely extra work, not a wrong answer; the confirming lookup makes the end-to-end result correct.
How do you get k independent hashes cheaply?
Double hashing (Kirsch–Mitzenmacher): derive all k from two base hashes — h_i = h1 + i·h2 mod m — same FP rate, far cheaper than k real hash functions. Cryptographic hashes are unnecessary here.
Tricky follow-ups
Can a Bloom filter ever say “definitely yes”?
No. Its two answers are “definitely no” and “maybe.” Certainty of presence always needs the backing store.
If I query an item I just added, can it return “not present”?
Never — that would be a false negative, which is impossible. Just-added items always read “maybe.”
Is the false-positive rate per-query or global?
Per query of a non-member. It doesn't “run out” — each independent non-member query has ≈ p chance. It rises as the filter fills.
Why did Bitcoin drop BIP37 Bloom filters?
Privacy. The items you query leak what you care about; a shared filter reveals a fingerprint of your data. Bloom filters are not a privacy or security mechanism.

  • ▸“Use it as a cheap local ‘probably not’ to skip an expensive disk/DB/network op in the common case.”
