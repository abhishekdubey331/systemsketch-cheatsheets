30-Day System Design · Day 14

2FA — setup & recovery

Your authenticator works on a plane because nothing is ever sent. Here's how that works — and the part almost everyone skips.

The one idea
Your phone and the server never talk. They share a secret and a clock — and both run the same maths.
How it works — TOTP in four steps
  1. You scan the QR code. That QR is a random secret (a base32 string). Scanning copies it onto your phone — the server already had it.
  2. Time gets chopped into 30-second slots. Both sides compute the same slot number: floor(unix_time / 30).
  3. Your phone hashes the slot with the secret — HMAC(secret, slot) — and truncates the result to six digits.
  4. The server runs the identical maths. Same secret, same slot ⇒ same six digits. Nothing crossed the network, so airplane mode changes nothing.

Standard: RFC 6238 (TOTP), built on RFC 4226 (HOTP). It's a shared-secret scheme — hold that thought, it matters at the bottom of this page.

The catch nobody mentions

Clocks drift, so servers accept the neighbouring slots too — typically ±1, giving a window of roughly 90s instead of 30. That's why a code you type at the very last second still works.

It's a dial, not a setting: the wider that window, the longer a stolen code stays valid.
Not all 2FA is equal
Method Stops a
leaked password		 Stops
phishing		 Why
SMS code ✓ ✗ Your number can be taken over by SIM-swap or a port-out. And you can still read the code out to a fake site.
Authenticator app ✓ ✗ Works offline, no phone number to steal. But nothing stops you typing the code into a convincing fake login page.
Push “approve” ✓ ~ Better if it shows a number to match. Plain yes/no prompts can be spammed until someone taps approve.
Passkey / security key ✓ ✓ The credential is bound to the real domain, so a lookalike site simply can't use it. The only row that survives phishing.

Rule of thumb: anything beats a password alone, and an app beats SMS. If a service offers passkeys, that's the upgrade worth making.

Set it up — the order matters
  1. Find it under Settings → Security → Two-factor authentication. Can't see it? Search “<service> two-factor authentication”.
  2. Choose the authenticator app option over SMS whenever both are offered.
  3. Save the recovery codes before you close that screen. Most services show them exactly once. This is the step people skip, and it's the one that costs them the account.
  4. Test it now — sign out and back in while the setup page is still open. Discovering it's broken next month is a very different afternoon.
  5. Add a second factor if allowed: a spare device, or a hardware key kept somewhere else.
  6. Turn off SMS fallback once something stronger works. Your real security level is your weakest enabled factor, not your strongest.
Recovery codes — where they actually go
Do
  • ✓Your password manager — in a separate entry from the password.
  • ✓Printed on paper, somewhere physical you'd trust with a spare key.
  • ✓A second copy in a different place from the first.
Don't
  • ✗A screenshot in your camera roll — it syncs to the very cloud account you're protecting.
  • ✗Emailed to yourself — that inbox is usually the account behind every password reset.
  • ✗The same manager entry as the password. One breach shouldn't hand over both factors.

Each code is single-use. Cross one off every time you spend it, and regenerate the set when you're running low — a fresh set invalidates the old one.

The lost-phone drill
  1. Sign in with a recovery code.
  2. Regenerate the recovery codes immediately — the old set is now partly spent and possibly on a device you no longer hold.
  3. Remove the lost device from the account's 2FA device list, so its codes stop working.
  4. Re-enrol your new phone and save the new codes.
  5. Then wipe the lost phone remotely. In that order — a remote wipe first can lock you out of the codes you still needed.

Do this for your email account first. It's the master key: whoever controls it can reset most of the others.

Say this in the interview
  • ▸“TOTP is an HMAC over a time counter — RFC 6238, on top of HOTP's RFC 4226.”
  • ▸“Neither side transmits the code. Both derive it from a shared secret and the current time step, which is why it works with no network.”
  • ▸“The acceptance window is a security-vs-usability dial: ±1 step forgives clock drift, but every extra step you accept extends the life of a stolen code.”
  • ▸“It's a shared-secret scheme, so the server stores something worth stealing — and the user can still be phished into typing a valid code. Passkeys fix both: asymmetric, and bound to the origin.”
  • ▸“Rate-limit verification attempts. Six digits is a million-wide space, which is not much if you allow unlimited guesses inside a 90-second window.”
