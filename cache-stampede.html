Cache Stampede — cheat sheet

The cache is the only reason your database survives normal traffic. Give every key the same lifetime and the shield becomes the weapon — all at once, at noon.

The one idea
A cache miss is cheap. Ten thousand at the same instant is an outage — because the database was only ever sized for what the cache let through.
The mental model — how the outage builds
1
11:00 — a batch job refills the cache. Every key it writes gets the same TTL, because that TTL is a constant in the config. Nothing is wrong yet; the cache is at 99.99% hit rate and the database sees a trickle.
2
The database was sized for that trickle. This is the part people skip. Connection pool, CPU, IOPS — all provisioned against post-cache traffic, maybe ~1 q/s, not against the 10,000 rps hitting the front door.
3
12:00 — every key expires in the same instant. One clock, one deadline. Nothing staggered them, because nothing was asked to.
4
Every in-flight request misses and goes to the origin. They don't queue politely — they're concurrent, and each one independently decides to rebuild.
5
The database falls over. Now it's self-sustaining: queries time out, so nothing repopulates the cache, so the next wave also misses. Retries add load. The cache stays empty for as long as the origin stays down.

Step 5 is the difference between a latency spike and an incident. A stampede that the origin absorbs is a graph you notice on Monday; a stampede that kills the origin is self-healing in the wrong direction — it will not recover on its own until you shed load.

The trap — where most candidates stop

Ask anyone how to fix a cache stampede and you'll get jitter — randomise the TTLs so keys stop landing on one clock. That is the right answer, and it is only the answer for the many keys case.

You cannot stagger a single cached copy.

One viral key has one expiry instant. Randomising its TTL moves that instant; it doesn't create more of them. When it goes, every concurrent request still misses together — jitter or not. Different problem, different fix: request coalescing.

Two shapes, often confused
ShapeTriggerWhat fixes it
Synchronised expiry Many keys, one TTL. Batch refill, deploy-time warm, or a cache flush. Jitter. Coalescing helps too, but jitter is what removes the correlation.
Hot-key expiry One key, huge concurrency. The trending item, the homepage, the config blob. Coalescing (or stale-while-revalidate / early refresh). Jitter does nothing here.

Two neighbours worth naming so you don't conflate them: cache penetration is traffic for keys that don't exist, so every request misses forever — fix with negative caching or a Bloom filter. Cache avalanche is the cache node or cluster itself going away — fix with replication, load shedding and a circuit breaker to the origin.

In a real system you'd ship rows 1 and 2 together — they address different halves of the same failure. Rows 3 and 4 are the upgrade when the rebuild is slow enough that making anyone wait for it is unacceptable.

Jitter — the one-liner
# spread expiries out, don't stack them. # ±10% is a default; widen for big sets. ttl = base + random.uniform(0, 0.1 * base) cache.set(key, value, ex=int(ttl))

Note the direction: jitter adds to the base rather than subtracting, so no key expires earlier than you intended. And it is a probabilistic fix — keys are unlikely to land together, not guaranteed apart.

Coalescing — the shape of it
value = cache.get(key) if value is not None: return value lock = f"lock:{key}" # SET NX PX — one caller wins, and the # lock auto-expires if that caller dies. if cache.set(lock, token, nx=True, px=5000): try: value = db.query(...) # the ONE cache.set(key, value, ex=jittered()) finally: release_if_owner(lock, token) return value # everyone else waits, then re-reads. # Do NOT spin, and do NOT fall through to # the database — that IS the stampede. sleep(0.05) return cache.get(key) or serve_stale()

The finally + ownership token matters: releasing a lock you no longer own (because yours expired and someone else took it) deletes their lock and reopens the gate. In Go this whole block is golang.org/x/sync/singleflight; most languages have an equivalent, and an in-process one is often enough.

Gotchas that bite in production
!
The lock TTL is shorter than the rebuild. The lock expires mid-query, a second caller takes it, and now you have two rebuilds — and if it's a write-through, possibly a lost update. Size the lock TTL off the p99 rebuild, not the median.
!
Unbounded waiters. You moved 9,999 requests off the database and onto your own service's threads, sockets and memory. That is the right trade — but cap the wait and fail fast past it, or you've relocated the outage rather than fixed it.
!
Jitter applied only on write, never on backfill. The batch job jitters; the lazy-fill path in the request handler uses the raw constant. Six weeks later the keys have re-synchronised. Put the jitter inside the setter so there is one place to get it right.
!
A cache flush or a cold restart is a stampede. Jitter doesn't help — every key is missing at once because you deleted them at once. Warm the cache before taking traffic, or ramp traffic in.
!
Retries turn a spike into a siege. Client retries on origin timeouts multiply the exact load that caused the timeout. Exponential backoff with jitter, plus a circuit breaker, or the origin never gets the quiet moment it needs to answer one query.
!
Negative results aren't cached. If a miss on a nonexistent key always reaches the origin, you have a permanent stampede that no TTL tuning fixes. Cache the "not found" too, with a short TTL.
Interview Q&A · 23 questions
The basics
What is a cache stampede?
A large number of concurrent requests all miss the cache for the same data at the same time and all go to the origin. Also called dogpile, thundering herd, or cache miss storm. The damage isn't the misses — it's that the origin is provisioned for post-cache traffic, so a burst of pre-cache traffic can exceed its capacity by orders of magnitude.
Why does giving every key the same TTL cause an outage?
Because it correlates their failures. Independent expiries spread origin load smoothly over time; identical expiries collapse it into one instant. A batch job, a deploy-time warm or a cache flush all write thousands of keys within a second or two of each other, so a constant TTL means they die together too.
The database handled it yesterday. Why not today?
Yesterday it saw post-cache traffic. During a stampede it sees pre-cache traffic. With a 99.9% hit rate that's a 1000× step change in queries per second. The database isn't degraded — it's being asked to do a job it was never sized for.
Why doesn't the cache just repopulate and end the problem?
It can't, if the origin is saturated. The queries that would fill the cache are the ones timing out. So the cache stays empty, the next wave also misses, and retries pile on. The failure is self-sustaining until you shed load — which is why it's an incident and not a spike.
Is this the same as cache penetration or cache avalanche?
No, though they get lumped together. Penetration: requests for keys that don't exist, so every one misses forever — fix with negative caching or a Bloom filter. Avalanche: the cache node or cluster itself is gone — fix with replication, load shedding and a circuit breaker. Stampede: the keys are cacheable and the cache is healthy; they just expired together.
Jitter — and its limit
How does jitter fix it, exactly?
By decorrelating expiry times. Instead of ttl = 3600, use ttl = 3600 + rand(0, 360). Keys written in the same second now expire spread across a six-minute window, so the origin sees a slope instead of a cliff.
How much jitter?
Wide enough that the expected number of expiries per second is something the origin can absorb. Roughly: keys ÷ jitter_window ≤ origin_capacity. ±10% is a common default; a million keys refilled by one batch needs a much wider window than a thousand.
Add or subtract the random component?
Add. Subtracting means some keys expire earlier than your intended freshness bound, which quietly increases origin load and can violate whatever staleness contract the TTL represented.
Jitter is in. It's one viral key. Are you safe?
No — this is the trap. Jitter spreads keys apart from each other. A single key has one cached copy and therefore one expiry instant; randomising its TTL moves that instant but doesn't multiply it. When it expires, every concurrent request for it still misses together. You need request coalescing, early refresh, or stale-while-revalidate.
So when is jitter enough on its own?
When load is spread across many keys with no dominant one, and any single key's concurrency is low enough that a handful of simultaneous rebuilds is harmless. The moment you have a hot key — trending item, homepage, feature-flag blob — jitter alone stops being sufficient.
Coalescing and locks
What is request coalescing?
On a miss, exactly one caller acquires a per-key lock and rebuilds the value; every other caller waits and is then served that same result. N concurrent misses become one origin query. Also called singleflight, request collapsing, or a dogpile lock.
Per-key lock or one global lock?
Per key, always. A global lock serialises every rebuild in the system, so an unrelated slow key blocks everything — you've converted a stampede into a queue. The lock key is normally just lock:<cache_key>.
What if the lock holder crashes?
The lock must carry a TTL (SET NX PX), so it self-releases. Waiters must also cap their wait and take a fallback path — serve stale, return a degraded response, or fail fast — rather than blocking indefinitely on a holder that will never return.
Do you need a distributed lock — Redlock, ZooKeeper?
Almost never, and saying so is a good signal. Losing the lock here costs you one extra origin query, not correctness. A single-instance SET NX PX is the right tool; reaching for consensus means you've mistaken a performance optimisation for a mutual-exclusion requirement. (If the rebuild has side effects, that's a different problem and you shouldn't be doing it under a cache lock at all.)
Is a per-process lock good enough?
Often yes. With N app instances an in-process singleflight reduces the herd from 10,000 to N — which for N in the tens is usually well within origin capacity, with zero extra infrastructure and no lock-expiry edge cases. Reach for the shared lock when N is large or the rebuild is genuinely expensive.
What's the downside of coalescing?
Latency. Every waiter now pays the full rebuild time, so p99 for that key jumps to the rebuild duration. You also concentrate risk: if the one rebuild fails, everybody waiting gets an error simultaneously. Stale-while-revalidate is the answer when neither is acceptable.
Beyond the lock
How does stale-while-revalidate work?
Store a soft TTL alongside the value and keep a longer hard TTL. Past the soft TTL the first reader triggers an async refresh and is served the stale value immediately; everyone else keeps getting the stale value until the refresh lands. Nobody waits, and the origin sees exactly one query. The trade is bounded staleness — you must be able to say how stale is acceptable.
What is probabilistic early expiry?
Each reader independently decides, with a small probability, to refresh before the TTL. The probability rises as expiry approaches and scales with how long the recompute takes, so expensive values get refreshed earlier. Formalised as XFetch in "Optimal Probabilistic Cache Stampede Prevention" (VLDB 2015): recompute when now − delta × beta × ln(rand()) ≥ expiry. No locks, no coordination — the herd is dissolved statistically.
When would you just never expire the key?
When you can enumerate the hot keys and a background job can keep them fresh — homepage, config, top-N leaderboards. Reads then never miss. The cost is operational: a refresher you have to monitor, and a plan for what happens when it silently stops (stale data with no expiry is worse than no cache).
How do you defend the origin regardless?
Assume every upstream fix will eventually be missing or misconfigured. Bound the origin with a connection-pool cap, a concurrency limiter or queue with a hard ceiling, and a circuit breaker so callers fail fast instead of piling on. That's what keeps a stampede a latency spike instead of an outage.
Design & debugging
Design the cache layer for a trending-items feed.
Jitter every TTL inside the setter so there is one code path. Wrap the rebuild in per-key coalescing so a hot item costs one origin query. For the top few items, add stale-while-revalidate so readers never wait on a refresh. Cap waiters and cap origin concurrency. Emit hit rate, origin QPS and rebuild p99 per key so you can see a herd forming before it lands.
Your origin QPS spikes 1000× every hour on the hour. Diagnose it.
Hourly periodicity plus a step function is synchronised expiry: something writes a batch of keys with a constant TTL. Confirm by sampling TTLs on a random key set (TTL key) — if they cluster tightly, that's it. Fix by jittering at the setter. If instead one key dominates the miss log, it's hot-key expiry and you need coalescing, not jitter.
What would you alert on?
Not the origin's CPU — by then it's happening. Alert on cache hit rate dropping (leading indicator), origin QPS relative to its provisioned ceiling, and rebuild concurrency per key (if more than one rebuild is in flight for one key, coalescing is broken). A histogram of remaining TTLs will show correlation before it costs you anything.
Say this in the interview

  • ▸“A constant TTL correlates expiries. Jitter decorrelates them: ttl = base + rand(0, 0.1×base).”
  • ▸“Jitter for many keys, a per-key lock for one hot key. You cannot stagger a single cached copy.”
  • ▸“Coalescing needs a lock TTL, an ownership token and a capped wait — otherwise you've moved the queue into your own service.”
  • ▸“I wouldn't reach for a consensus lock. Losing it costs one extra query, not correctness — SET NX PX is the right tool.”
  • ▸“And I'd bound the origin anyway — concurrency limit plus circuit breaker — because every upstream fix eventually gets misconfigured.”
