Write-Ahead Log — the cheat sheet

You type the perfect Instagram caption and the app crashes. You reopen it — your draft is still there. The durability trick behind every reliable commit.

The one idea
Write down what you're about to do — and get that note onto disk — before you do it. Recovery is just replaying the notes.
The mental model

Your app auto-saves the caption to a local database on the phone. Editing the database file in place is risky: a row can be half-written when the process dies, leaving the file corrupt — not just stale, but unreadable. So the database doesn't touch the data file first. It appends the change to a log, forces that log to storage, and only then treats the change as committed. The data file catches up later, at its leisure. Crash? On restart, replay the log — the draft comes back. The log is the source of truth; the data file is a cache of it.

How it works — append, flush, then apply
1

Append the change to the log. Sequential write, no seeking. The data file is untouched.

log · in bufferLSN 41 · SET draft='6 months…' data page 7old value · unchanged
2

fsync() the log — this is the moment that matters. Only once the record is on stable storage is the change committed, and only then do you acknowledge the user.

log · on disk ✓LSN 41 · committed data page 7still old · that's fine
3

Apply to the data file whenever convenient — batched, in the background. The log leads; the data catches up.

log · on disk ✓LSN 41 data page 7pageLSN = 41 · applied
4

Crash between 2 and 3 → on restart, scan the log from the last checkpoint and redo every record whose LSN > pageLSN. Committed work returns; half-finished work is rolled back.

replayLSN 41 > pageLSN 40 → redo result✓ your draft is back

The write-ahead rule is literally the name: the log record must be durable before the data page it describes is written. Break that ordering and recovery can meet a data page it has no note for.

“Committed”

The commit record reached stable storage (fsync returned). It survives process crash, OS panic and power loss.

lives in → the log, on disk
on crash → redone during replay
safe to → tell the user “saved”
“Written” but not flushed

write() returned, but the bytes sit in the OS page cache. Survives a process crash — a power cut loses it.

lives in → RAM (page cache)
on power cut → gone, silently
never → ack the user on this
The guarantee (and the catch)
A WAL buys you atomicity + durability — a write is all-or-nothing, and once acknowledged it survives a crash. But only up to the last fsync. write() is not durability; if the log never truly hit the platter, the change is gone.
The dial — durability vs throughput

Every database exposes the same knob: how often do we fsync the log?

Memorize the trade: relaxing the flush loses recent commits, never consistency — the DB still comes back intact, just slightly in the past. That's why synchronous_commit=off is a legitimate production choice and turning off the WAL is not.

Checkpoints, and why the log doesn't grow forever

A checkpoint flushes dirty data pages and records “everything before LSN X is safely applied.” That does two jobs: recovery only has to replay from the last checkpoint (bounded restart time), and log segments before it can be recycled or archived. Checkpoint too rarely → long recovery + huge log; too often → constant I/O. Postgres ships WAL in 16 MB segments; SQLite calls the equivalent step a WAL checkpoint, folding the -wal file back into the main DB.

The torn-page problem: a power cut can leave a data page half-written — and redo assumes it can read the old page to patch it. Fixes: Postgres full-page writes (the first change to a page after a checkpoint logs the whole page), InnoDB's doublewrite buffer. This is why WAL files are bigger than “just the diffs.”

Where it's used (it's everywhere)

Databases: PostgreSQL WAL, MySQL/InnoDB redo log, SQLite WAL mode, Oracle redo, SQL Server transaction log. Storage engines: RocksDB / LevelDB / Cassandra / HBase write to a commit log before the in-memory memtable. Filesystems: ext4, XFS and NTFS journal metadata the same way. Consensus: Raft and etcd persist entries to a log before applying them to the state machine. Streaming: Kafka is a durable append-only log, exposed as a product.

The second superpower: because the log is an ordered record of every change, you get replication free — ship the same log to a replica and it converges to the same state. That's Postgres streaming replication, MySQL binlog, and the basis of point-in-time recovery (restore a base backup, replay the log to 14:32) and change data capture.

Interview Q&A

Tap a question. From fundamentals to the tricky follow-ups.

Fundamentals
What is a write-ahead log in one sentence?
An append-only log of intended changes that is forced to durable storage before the corresponding data pages are modified — so a crash can always be repaired by replaying it.
What exactly is the “write-ahead rule”?
The log record describing a change must reach stable storage before the data page it describes is written to disk. Plus the commit rule: a transaction isn't committed until its commit record is durable.
Why not just write to the data file directly?
A data-file update is a random, multi-byte, possibly multi-page mutation. Crash halfway and the row or page is corrupt — you can't even tell what the old value was. The log makes the change atomic: either the record is fully there (redo it) or it isn't (ignore it).
Which ACID properties does it give you?
Atomicity (all-or-nothing via redo/undo) and Durability (committed survives crash). Isolation comes from locking/MVCC, not the WAL — a common mix-up.
Redo vs undo — what's the difference?
Redo re-applies committed changes that never reached the data file. Undo rolls back changes from transactions that never committed. ARIES does both: repeat history (redo everything), then undo the losers.
Durability & fsync
Isn't a successful write() enough?
No — and this is the single most common miss. write() only copies into the OS page cache. It survives your process crashing, but a power cut loses it. Durability requires fsync()/fdatasync() to return.
So when is a transaction actually “committed”?
The instant its commit record is durably on disk. Not when the SQL ran, not when write() returned. Only after that may you acknowledge the client — otherwise you've promised something you can lose.
fsync is slow. How do you keep throughput up?
Group commit: batch concurrent transactions and flush them with one fsync, so the cost is amortized across N commits. Also use fdatasync (skips metadata), keep the log on its own fast device, and let the log write be sequential.
Can you turn the flush off?
Yes, and it's a real choice: synchronous_commit=off / innodb_flush_log_at_trx_commit=2. You risk losing the last few hundred ms of commits — but the database still recovers to a consistent state. Losing recent data ≠ corruption.
What if the disk lies about fsync?
Consumer drives with a volatile write cache can ack a flush before the data is on the platter — durability silently breaks. Mitigations: enable write barriers / FUA, disable the volatile cache, or use drives with power-loss protection. Historically the cause of many “impossible” corruptions.
Recovery
Walk me through crash recovery.
Analysis — start at the last checkpoint, find dirty pages and in-flight transactions. Redo — replay forward, re-applying every record whose LSN > pageLSN. Undo — roll back transactions with no commit record. That's ARIES.
What's an LSN and why does it matter?
A monotonically increasing log sequence number. Each page stores the LSN of the last record applied to it, so recovery can ask “has this page already seen this record?” That's what makes redo idempotent.
Why must replay be idempotent?
Because recovery itself can crash and restart. Replaying the same record twice must be a no-op — guaranteed by the LSN > pageLSN check. Without it, a crash during recovery could double-apply a change.
What is a checkpoint and why do you need one?
A point where dirty pages are flushed and “everything before LSN X is applied” is recorded. It bounds recovery time (replay only from there) and lets old log segments be recycled. Without checkpoints, restart time and log size grow without limit.
What's a torn page and how is it handled?
A power cut mid-page-write leaves a page partially updated — redo can't safely patch it because its “before” image is garbage. Postgres logs the full page image on first touch after a checkpoint; InnoDB uses the doublewrite buffer.
Systems & design
Design: draft auto-save that survives a crash.
Local DB (SQLite/Room) in WAL mode. On each edit, write the change and commit — one append + flush, cheap enough per keystroke if you debounce. On relaunch the engine replays its WAL automatically and the draft is there. Set synchronous=NORMAL for keystrokes (fast, may lose the last moment) and FULL before backgrounding.
How does WAL enable replication and PITR?
The log is a totally ordered record of every change. Ship it to a replica and it converges to identical state (Postgres streaming replication, MySQL binlog). Keep it alongside a base backup and you can replay to any point in time. Also the foundation of CDC (Debezium reads the log).
Where does WAL show up outside databases?
Filesystems (ext4/XFS/NTFS journaling), LSM engines (RocksDB/Cassandra commit log in front of the memtable), consensus (Raft persists entries before applying them), and Kafka, which is a durable append-only log sold as a product.
How does WAL interact with an LSM tree?
Writes go to the commit log (durability) and the in-memory memtable (readability). When the memtable flushes to an SSTable, the covering log segment can be discarded. The WAL exists purely to protect the memtable, which is volatile.
Where do you put the WAL for performance?
Ideally a separate, low-latency device, since commit latency is bound by log fsync and the access pattern is sequential — it shouldn't contend with random data-file I/O. Postgres exposes this by moving pg_wal to its own volume.
Tricky follow-ups
WAL writes everything twice — isn't that slower?
Usually faster. The log write is a small sequential append; the data write it replaces is a random page write. You trade random I/O now for sequential I/O now plus batched, coalesced random I/O later — and many updates to the same page collapse into one flush.
Does a WAL protect against disk failure or bad code?
No. It protects against crash and power loss only. A dead disk, a corrupted file, an rm -rf, or a bug writing wrong values are all faithfully replayed. That's what backups and replicas are for — different failure domain.
The WAL keeps growing and filled my disk. Why?
Something is pinning segments: a stale replication slot, an idle-in-transaction session, a failing archive command, or checkpoints too far apart. The log can't recycle past the oldest thing still needing it — a classic Postgres outage.
Group commit increases latency for a single transaction. Justify it.
One transaction waits a few extra ms to join a batch, but throughput rises roughly with batch size because fsync cost is amortized. Under load, p99 usually improves — without batching, every commit queues behind its own flush.
Is a WAL the same as an undo log?
Related but distinct. The WAL is the durable stream of changes; redo lives there. Undo information (old values, for rollback and MVCC reads) may live in the same log (Postgres) or a separate structure (InnoDB's undo tablespaces). ARIES logs both and even logs its undo work as compensation records so undo survives a crash too.
Say this in the interview

  • ▸“Committed means the commit record is fsync'd — not that write() returned. Page cache is not durability.”
  • ▸“Recovery = redo from the last checkpoint, then undo the losers. LSN > pageLSN makes replay idempotent.”
  • ▸“It's faster despite writing twice — a sequential append replaces a random page write, and fsyncs batch via group commit.”
  • ▸“Free bonus: the log is replication, PITR and CDC. Relaxing the flush loses recent commits, never consistency.”
